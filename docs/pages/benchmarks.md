# Benchmarks

All numbers on this page are reproduced from the committed benchmark outputs
(`bench/distfind/results.md` and `bench/distfind/cc_results.md`). They are measurements,
not estimates.

### Summary

- Backends available on the benchmark machine: `['cpu', 'gpu']`.
- **`cpu / gpu` speedup**: min 0.32×, max 2.32×, median 1.39× — values below 1 mean the
  CPU was faster, which is expected for small codes where GPU dispatch overhead dominates
  (the hybrid dispatcher is what keeps the GPU from being a net slowdown).
- **All distances matched**: GPU's best-of-retries value equals the CPU value everywhere.

#### GPU determinism

GPU was run 3× per code as a determinism probe and returned the **same correct distance
every time** on all codes. (An earlier stale-device-buffer bug — the buffer cache keyed on
host-pointer identity — was fixed by keying on a unique per-solve token.) A `*` would flag
any code whose GPU runs disagreed; there are none. Reported GPU times are the fastest
of the probe runs.

## Connected cluster vs BZ

Generated by `bench/distfind/cc_benchmark.py`. `cc` is qubitserf connected cluster; `bz`
is qubitserf Brouwer–Zimmermann.

> [!NOTE]
> These numbers predate the removal of the `max_weight` cap from the API. The
> `[lower, upper]` cells below are BZ runs that were stopped by that now-removed cap;
> BZ on those codes now simply runs until the benchmark's per-method time budget trips
> and is reported as a timeout. The distances and the `cc` timings are unaffected.

| code | n | d | cc | bz |
|---|---|---|---|---|
| steane [[7,1,3]] | 7 | 3 | d=3 (1.4ms) | d=3 (245us) |
| shor [[9,1,3]] | 9 | 3 | d=3 (824us) | d=3 (274us) |
| toric L=6 [[72,2,6]] | 72 | 6 | d=6 (1.1ms) | d=6 (2.1ms) |
| surface L=6 [[61,1,6]] | 61 | 6 | d=6 (1.0ms) | d=6 (3.1ms) |
| bb [[72,12,6]] | 72 | 6 | d=6 (1.2ms) | [6,6] capped (3.2ms) |
| toric L=9 [[162,2,9]] | 162 | 9 | d=9 (1.9ms) | [7,9] capped (6.02s) |
| toric L=10 [[200,2,10]] | 200 | 10 | d=10 (2.5ms) | [8,10] capped (27.51s) |
| **gross [[144,12,12]]** | 144 | 12 | **d=12 (377.6ms)** | [8,12] capped (3.87s) |

### Takeaway

- On sparse codes whose BZ lower bound is weak (bivariate-bicycle, large toric),
  connected cluster certifies the exact distance in well under a second, while
  Brouwer–Zimmermann cannot prove it in tractable time. On small codes both methods
  agree.
- Connected cluster certifies the gross code `[[144, 12, 12]]` in **~0.4 s** (377.6 ms),
  where the BZ run got no further than a lower bound of 8 before it was stopped.

## Reproducing the benchmarks

All scripts run from the repository root, with NumPy available; on the project's machine
that is the `sage_env` interpreter:

```bash
# BZ: CPU vs GPU -> writes bench/distfind/results.md
PYTHONPATH=python python bench/distfind/benchmark.py

# connected cluster vs BZ -> writes bench/distfind/cc_results.md
PYTHONPATH=python python bench/distfind/cc_benchmark.py

# toric/surface scaling -> bench/distfind/scaling.md
PYTHONPATH=python python bench/distfind/scaling.py

# the IBM gross code [[144,12,12]]: distance and wall time per backend
PYTHONPATH=python python bench/distfind/gross_code.py
```

Notes:

- GPU is run several times per code as a regression guard; the script flags any
  disagreement and reports the fastest run.
- Absolute timings depend on your hardware; the **distances** and the relative orderings
  are what the benchmarks assert.
